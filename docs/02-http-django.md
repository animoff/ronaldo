# HTTP и путь запроса в Django

**До начала:** урок о Python и работающий сервер. **Результат:** вы умеете проследить путь от адреса в браузере до SQL-запроса и HTML-ответа.

## Браузер разговаривает сообщениями

HTTP-запрос состоит из метода, пути, заголовков и иногда тела. Ответ содержит статус, заголовки и тело. HTML и JSON — разные представления данных, передаваемые одним протоколом.

```text
GET /catalog/?q=python&page=1 HTTP/1.1
Host: localhost:8000
```

Путь `/catalog/` выбирает обработчик, а query string задаёт поиск и страницу. GET предназначен для чтения: переход по ссылке не должен оформить заказ. POST передаёт действие, например добавление товара в корзину. При повторном POST действие может выполниться снова, если приложение не защитило его идемпотентностью.

У HTTP нет встроенной памяти о пользователе. Cookie несёт идентификатор сессии; Django по нему находит состояние. Соединение и сессия — разные понятия. Один пользователь создаёт множество HTTP-запросов.

## Маршрут в нашем проекте

```text
Браузер → сервер → middleware → URL resolver → view
                                           ↓
                                     сервис / ORM → БД
                                           ↓
Браузер ← HTTP-ответ ← middleware ← шаблон или JSON
```

`ronaldu/urls.py` соединяет маршруты приложений. `main/urls.py` направляет каталог в `main/views.py`. View принимает `request`, получает и проверяет параметры, выбирает данные, возвращает ответ. Шаблон отвечает за представление, а не за списание остатков.

Django сначала выполняет middleware запроса в настроенном порядке, а ответа — в обратном. Middleware подключает сессии, аутентификацию, CSRF-защиту и другие сквозные механизмы. Это не место для всей бизнес-логики магазина.

```python
# Упрощённый пример, а не замена существующего view.
from django.shortcuts import get_object_or_404, render
from main.models import Product


def detail(request, slug):
    product = get_object_or_404(Product, slug=slug, is_active=True)
    return render(request, "main/product_detail.html", {"product": product})
```

`get_object_or_404` превращает отсутствие товара в 404. `render()` рендерит шаблон с контекстом и создаёт `HttpResponse`. Название переменной в контексте — договор между Python-кодом и шаблоном.

## Статусы и перенаправления

`200` означает успешный ответ, `302` — временный переход, `400` — некорректный запрос, `403` — отказ в доступе, `404` — ресурс не найден, `405` — неподдерживаемый метод, `500` — ошибка сервера. Для JSON API отсутствие аутентификации отдельно выражается статусом `401`.

После успешной HTML-формы обычно используется Post/Redirect/Get: POST изменяет состояние, сервер отправляет redirect, браузер делает GET страницы результата. Обновление страницы тогда повторит чтение. Это полезно для интерфейса, но само по себе не защищает от двух параллельных POST.

Используйте именованные маршруты (`main:product_detail`, `commerce:cart`) через `reverse()` и `{% url %}`. Жёстко записанный адрес легко забыть обновить при реорганизации URL.

## Практика

1. Откройте вкладку Network в инструментах браузера. Загрузите каталог и найдите метод, статус, `Content-Type`.
2. Добавьте товар в корзину. Найдите POST и следующий GET после redirect.
3. Перейдите к несуществующему товару. Ожидайте 404, а не страницу с сообщением об успешной покупке.
4. В `main/views.py` найдите использование `request.GET`. Объясните, почему поисковый текст не нужно хранить в глобальной переменной Python.
5. Найдите путь `/learn/` в URL-конфигурации и проследите его до шаблона.

**Проверка:** нарисуйте путь запроса каталога и подпишите, где появляется QuerySet, где HTML, а где статус ответа.

**Типичные ошибки:** изменение данных через GET; обращение к базе из шаблонной логики; ожидание, что Python-переменная сохранится между процессами; путаница 404 с падением приложения.

**Самопроверка:** почему redirect порождает новый запрос? Почему два открытых окна могут использовать одну корзину? Где нужно менять оформление страницы, а где правило доступности товара?

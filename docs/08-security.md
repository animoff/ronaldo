# Безопасность: границы доверия и настройки

**До начала:** формы, сессии, ORM и тесты. **Результат:** вы знаете, какие данные нельзя принимать на веру и как проверить основные защиты проекта.

## Главный принцип: клиент сообщает намерение

Клиент может попросить купить две единицы товара. Он не определяет достоверную цену, владельца заказа, остаток или статус оплаты. Эти значения устанавливает сервер. Даже hidden-поле, readonly-элемент и собственный JavaScript пользователь может изменить.

Проверяйте данные на входе и правила в месте совершения операции. Ограничения БД защищают последнюю границу. Проверка доступа обязательна для каждого объекта: знание номера заказа не даёт права видеть адрес доставки.

## Защиты Django и их пределы

**SQL-инъекция.** ORM передаёт значения параметрами. Не вставляйте пользовательский текст в raw SQL через f-строки. Самостоятельный SQL допустим, но требует параметризации и понимания границ.

**XSS.** Шаблоны по умолчанию экранируют текст. Не помечайте отзыв или имя пользователя как `safe`. Учебные Markdown-страницы берутся из контролируемых файлов репозитория; это другая граница доверия, чем публикация пользовательского HTML. При добавлении такого функционала потребуется отдельная политика sanitization.

**CSRF.** Cookie-аутентификация требует проверки происхождения действия. Сохраняйте middleware и токены в POST-формах. GET не должен удалять заказ или завершать сессию.

**Пароли.** Django хеширует пароли с солью и проверяет их через поддерживаемые API. Не логируйте пароль и не отправляйте его в письме после регистрации. Восстановление пароля — отдельный поток с ограниченным сроком токена; он не реализуется выдачей исходного пароля.

## Настройки разработки и production

`DEBUG=1` помогает локальной отладке, но подробная страница ошибки может раскрыть внутреннее устройство приложения. Перед публикацией используйте `DEBUG=0`, отдельный `SECRET_KEY`, конкретный `ALLOWED_HOSTS` и HTTPS. Проверяйте актуальные имена и значения в `.env.example` и `ronaldu/settings.py`.

`SECRET_KEY` участвует в подписи данных; это не пароль базы. Нельзя коммитить реальные секреты, вставлять их в README, скриншоты или traceback. `.env` — локальный удобный способ конфигурации, а не секретное хранилище сам по себе. Для сервера используйте защищённые переменные окружения или менеджер секретов и ограниченные права доступа.

```bash
python manage.py check --deploy
```

Команда ищет типовые проблемы настроек. Предупреждения на локальном HTTP ожидаемы, но перед production нужно разобрать каждое применимое. Зелёная проверка не является аудитом бизнес-логики.

Не включайте HSTS и доверие proxy-заголовкам вслепую. Сначала настройте HTTPS и границу доверенного reverse proxy. Ошибочное доверие `X-Forwarded-Proto` от любого клиента может нарушить предположения безопасности.

## Чего ещё требует реальный публичный сервис

Нужны ограничение частоты входа, мониторинг подозрительных событий, обновление зависимостей, защищённая обработка файлов, резервные копии и проверка восстановления. Учебный проект не заявляет наличие всех этих механизмов. `ImageField` не делает произвольную загрузку полностью безопасной: нужны лимиты размера, проверка содержимого и отдельная безопасная раздача media.

Не собирайте лишние персональные данные. Адрес доставки нельзя писать в общедоступный лог ради диагностики. Права администраторов выдавайте по необходимости: `is_staff` и `is_superuser` — разные уровни возможностей.

## Практика

1. Введите в поиск строку `<script>alert(1)</script>`. Она не должна исполняться как JavaScript.
2. Убедитесь, что чужой заказ недоступен и через HTML, и через API.
3. Найдите секреты в `.env.example`: там должны быть объяснения или демонстрационные placeholders, а не реальные ключи.
4. Выполните `check --deploy` и для каждого сообщения запишите, какая настройка и какое требование окружения его устраняют.

**Проверка:** можете ли вы назвать доверенный источник для цены, владельца заказа и адреса возврата после входа?

**Типичные ошибки:** использовать `ALLOWED_HOSTS=*` как универсальное исправление; выключать CSRF ради формы; скрывать ошибку вместо устранения; считать секретным всё, что не видно в интерфейсе.

**Самопроверка:** чем XSS отличается от CSRF? Почему администраторский пароль нельзя выдавать всем участникам проекта? Когда экранирование текста не решает проблему небезопасного URL?

# Формы, аутентификация, сессии и права

**До начала:** HTTP и модели. **Результат:** вы различаете проверку данных, установление личности и проверку доступа.

## Три разных вопроса

Валидация спрашивает: «Допустимы ли эти данные?» Аутентификация: «Кто сделал запрос?» Авторизация: «Можно ли этому пользователю выполнить действие над этим объектом?» Успешный вход не даёт доступ ко всем заказам магазина.

Все входящие значения считаются недоверенными. Ограничение `min=1` в HTML удобно человеку, но запрос можно отправить без браузера. Сервер снова проверяет количество, существование товара, остаток и пользователя.

## Form превращает текст в понятные значения

В `commerce/forms.py` находятся формы регистрации и оформления. View связывает форму с `request.POST`, вызывает `is_valid()`, а после успеха использует `cleaned_data`. Последний содержит уже преобразованные и проверенные значения.

```python
# Общая схема обработки HTML-формы.
form = CheckoutForm(request.POST or None)
if request.method == "POST" and form.is_valid():
    address = form.cleaned_data["address"]
    # Далее вызывается сервис оформления заказа.
```

Это схема, не готовая замена существующего view: реальный обработчик также проверяет корзину и ключ повторной отправки. Ошибки поля связываются с конкретным вводом, ошибки формы — с действием в целом. При неуспехе нужно показать форму и сообщения, сохранив введённые безопасные значения.

`ModelForm` помогает строить форму из модели. Указывайте разрешённые поля явно: `fields = "__all__"` в публичной форме может неожиданно открыть служебное поле после изменения модели.

## Вход и пароль

Регистрация использует механизмы Django для создания пользователя и валидации пароля. Пароль нельзя сохранять обычным присваиванием `user.password = raw_password`: методы `set_password()` и `create_user()` применяют настроенный хешер и соль. Хеширование необратимо; шифрование, напротив, предполагает возможность восстановления.

При входе Django проверяет пароль и связывает сессию с пользователем. В дальнейших запросах `request.user` становится аутентифицированным пользователем. Выход реализован через POST: ссылка GET не должна незаметно менять состояние сессии.

Cookie с идентификатором сессии нужно защищать. `HttpOnly` мешает JavaScript читать cookie, `Secure` ограничивает передачу HTTPS, `SameSite` уменьшает некоторые межсайтовые риски. Ни один атрибут не отменяет остальные проверки.

## CSRF и владелец заказа

Если браузер автоматически отправляет cookie, посторонний сайт может попытаться заставить его выполнить действие. Django сопоставляет CSRF-токен формы и ожидаемое состояние. В HTML-формах есть `{% csrf_token %}`. Это защита от подделки запроса, а не доказательство бизнес-права.

Заказ выбирается с учётом владельца:

```python
order = get_object_or_404(Order, pk=pk, owner=request.user)
```

Так чужой идентификатор не открывает чужие данные. Скрытая кнопка в шаблоне не заменяет эту проверку. `login_required` защищает от анонимного пользователя, но не проверяет принадлежность конкретного заказа.

## Практика

1. Зарегистрируйте двух пользователей в разных браузерных сессиях.
2. Создайте заказ первым и попробуйте открыть его адрес вторым. Ожидайте отказ, а не сведения о доставке.
3. Отправьте форму с пустым адресом. Убедитесь, что заказ не создан и остаток не изменён.
4. Найдите `{% csrf_token %}` в шаблонах корзины, регистрации и выхода. Удалять защиту ради устранения 403 не нужно: сначала исследуйте cookies и токен.
5. В административном интерфейсе посмотрите, как хранится пароль тестового пользователя: там должен быть формат хешера, а не исходный текст.

**Проверка:** вы можете указать отдельное место проверки количества, входа и владельца заказа.

**Типичные ошибки:** доверять hidden-полю `user_id`; сохранять сырой пароль; сравнивать только ID из URL без ограничения владельцем; считать CSRF-токен универсальным разрешением.

**Самопроверка:** почему авторизация нужна и для чтения? Чем сессия отличается от cookie? Почему права проверяются на сервере даже при скрытой кнопке?

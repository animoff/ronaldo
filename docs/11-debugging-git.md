# Отладка, Git и рабочий процесс разработчика

**Перед уроком:** запустите сайт и тесты. Цель — научиться получать доказательства, а не менять код наугад.

## Читаем traceback

Начните с типа исключения и сообщения в конце. Затем найдите ближайшую строку своего кода в стеке. Зафиксируйте запрос, входные данные, пользователя и состояние базы. Повторите ошибку самым коротким способом. Например, `TemplateDoesNotExist` — поиск шаблона, `NoReverseMatch` — имя URL/аргументы, `OperationalError` — соединение или SQL, а не автоматически «Django сломался».

```bash
python manage.py check
python manage.py showmigrations
python manage.py test commerce --verbosity 2
python manage.py shell
```

Команды выполняйте из каталога с `manage.py` и в активном venv. `python -c "import sys; print(sys.executable)"` показывает используемый интерпретатор. `python -m pip` использует pip именно этого Python.

## Исследуем данные и запросы

В Django shell импортируйте модель, найдите конкретную запись и проверяйте предположения:

```python
from main.models import Product
qs = Product.objects.filter(is_active=True).select_related("category")
print(qs.query)  # SQL структуры запроса, не ручная конкатенация SQL.
print(qs.count())
print(qs.first())
```

Вывод `qs.query` помогает понять запрос; для оценки производительности нужен реальный план и измерение. Не выводите SQL с персональными данными в общедоступный лог. `breakpoint()` останавливает локальный процесс для исследования переменных; не оставляйте его в публичном сервере.

Django test client проверяет обработчики без настоящего TCP-сервера. Для сетевого smoke test нужны реальный процесс и запрос, например `curl -i /health/` с адресом вашего локального сервера. Тестовый клиент не проверяет TLS, reverse proxy и реальную раздачу статики.

## Как читать логи

Здесь Python logging пишет в stdout/stderr — это удобно для контейнера. INFO фиксирует нормальные события, WARNING — подозрительное, ERROR — сбой. Исключение логируют на границе, где его обрабатывают. Не логируйте пароли, cookie, секретные заголовки, полные адреса доставки и всё тело запроса «на всякий случай».

Следующее упражнение — request ID: middleware создаёт идентификатор, добавляет в ответ и контекст логов. Это связывает события одного запроса. Затем измерьте p50/p95/p99 задержки: среднее может скрывать медленные запросы.

## Git: маленькая проверяемая задача

В обычной локальной работе создайте ветку для конкретной задачи:

```bash
git status
git switch -c feature/order-note
# Внесите небольшое изменение и его тест.
python manage.py test
git diff --check
git diff
git add commerce/models.py commerce/migrations/
git commit -m "Add optional note to orders"
```

Список файлов в примере замените фактически изменёнными. Не используйте слепой `git add .`, не просмотрев diff. Проверьте, что секреты, база, фотографии и логи исключены через `.gitignore`. Миграции и lock/pinned requirements, наоборот, нужны в Git.

Облачная задача уже изолирована: используйте существующий checkout; дополнительный worktree для обычной задачи не требуется.

## Как написать полезный PR

Опишите проблему, новое поведение и проверки. Например: «Покупатель может оставить комментарий к заказу до 300 символов. Пустое значение допустимо; превышение лимита возвращает ошибку формы. Проверены сохранение, границы длины и права просмотра». Укажите миграцию и совместимость, если они затронуты. Скриншот помогает оценить интерфейс, но не доказывает транзакционную корректность.

При конфликте merge изучите обе стороны и намерение изменений. Удалить маркеры конфликта недостаточно: запустите связанные тесты и проверьте миграционный граф.

## Диагностическая таблица

| Симптом | Что проверить первым |
|---|---|
| Нет Django | Интерпретатор и установка requirements |
| Нет таблицы | Настройки выбранной БД, `showmigrations`, `migrate` |
| 403 формы | CSRF cookie/hidden field, origin, HTTP/HTTPS |
| 404 товара | slug, is_active, URL namespace |
| CSS отсутствует | static URL, collectstatic, DEBUG, manifest |
| SQLite locked | Конкурентные записи; для гонок используйте PostgreSQL |
| 500 только в production | Логи, env, ALLOWED_HOSTS, статика и доступность БД |

## Практика и проверка

В своей ветке сломайте имя шаблона одной страницы. Найдите ошибку по traceback, напишите падающий тест и исправьте. Затем проверьте, что тест ловит повторную поломку. Не оставляйте намеренную ошибку в рабочей ветке.

**Самопроверка:** чем воспроизведение отличается от предположения? Что даст failing test коллеге? Почему изменение настроек без понимания причины может скрыть дефект?

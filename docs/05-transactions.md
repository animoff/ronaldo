# Корзина, деньги, транзакции и повторные запросы

**До начала:** ORM, формы и права. **Результат:** вы понимаете, почему оформление заказа — отдельный сценарий с гарантиями целостности.

## Корзина ещё не заказ

В `commerce/cart.py` корзина хранит идентификаторы вариантов товара и количество в сессии. Цена берётся с сервера. Если клиент передаст собственную цену, это не должно повлиять на итог. Строковые ключи сессии преобразуются осторожно: повреждённое или устаревшее состояние возможно даже без злоумышленника.

Добавление в корзину не резервирует товар. Пока покупатель думает, остаток может измениться. Поэтому проверка на странице товара полезна для интерфейса, а окончательная проверка выполняется во время оформления.

`ProductSize` — складская единица: конкретный товар в конкретном размере. На один и тот же товар размера M и размера L могут быть разные остатки.

## Сервис выражает бизнес-сценарий

В `commerce/services.py` собрана логика создания заказа. View занимается HTTP и формой; сервис проверяет бизнес-условия и меняет данные. Так одну операцию можно вызывать из другого интерфейса без копирования правил.

Сценарий состоит из связанных действий: проверить позиции, списать остатки, создать заказ, сохранить строки с ценами, вернуть результат. Снимок цены нужен, чтобы изменение каталога завтра не изменило сегодняшнюю покупку. Деньги рассчитываются с `Decimal` и сохраняются в decimal-полях.

## Почему нужна транзакция

Допустим, первый товар удалось списать, а второго уже нет. Без транзакции магазин потеряет остаток первого и не создаст полноценный заказ. `transaction.atomic()` объединяет изменения: либо они сохранятся вместе, либо ошибка откатит всю операцию.

```python
# Иллюстрация одного шага; полный сценарий смотрите в services.py.
with transaction.atomic():
    changed = ProductSize.objects.filter(
        pk=sku_id, stock__gte=quantity
    ).update(stock=F("stock") - quantity)
    if changed != 1:
        raise InsufficientStock("Недостаточно товара")
```

`F()` выполняет арифметику в БД. Условие `stock__gte` и уменьшение выполняются одним UPDATE: нельзя успешно списать отсутствующее количество. Схема «прочитать значение → уменьшить в Python → save» без защиты допускает потерянные изменения.

На PostgreSQL `select_for_update()` блокирует выбранные строки до окончания транзакции. Для нескольких позиций одинаковый порядок захвата уменьшает риск deadlock. SQLite не реализует те же блокировки строк: успешные тесты на SQLite не доказывают конкурентную корректность на боевой БД. Блокировки также не отменяют обработку таймаутов и ошибок соединения.

## Идемпотентность — повтор без нового результата

Двойной клик, повтор браузера после сетевой ошибки или два вкладочных запроса возможны в нормальной работе. Ключ оформления позволяет распознать уже выполненную операцию. Ключ связан с текущим пользователем и должен проверяться сервером; уникальное ограничение в БД закрывает гонку двух одновременных запросов.

CSRF и идемпотентность решают разные задачи: первый проверяет допустимость межсайтового источника действия, вторая предотвращает повторное создание результата. Ключ повторной отправки не заменяет проверку владельца.

После успешного оформления корзина очищается. Ошибка не должна молча уничтожать содержимое. Внешние действия — письмо или задача — обычно ставят после коммита через `transaction.on_commit()`, чтобы не сообщить о заказе, который потом откатился. В этом проекте настоящая платёжная интеграция не реализована.

## Практика

1. Оформите заказ и сравните сохранённую цену строки с ценой каталога.
2. Измените цену товара через admin. Ранее созданный заказ должен сохранить исходную сумму.
3. Попытайтесь заказать больше остатка. Проверьте количество заказов и остатки всех затронутых позиций.
4. Найдите тест повторного оформления с тем же ключом. Ожидается один заказ и одно списание.

**Проверка:** объясните, что случится при исключении после первого UPDATE и до создания второй строки заказа.

**Типичные ошибки:** доверять клиентскому итогу; вызывать платёжный HTTP API внутри длинной транзакции; считать redirect защитой от дубля; ловить ошибку БД внутри `atomic()` и продолжать работу как будто транзакция исправна.

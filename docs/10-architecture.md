# Архитектура: от понятного монолита к росту

**Перед уроком:** проследите оформление заказа из view в сервис и базу. Цель — выбирать архитектуру под проблему, а не по списку модных технологий.

## Разделение ответственности в проекте

| Слой | Отвечает за | Пример |
|---|---|---|
| URL | Выбор обработчика | `commerce/urls.py` |
| View | HTTP, вход, доступ, ответ | `commerce/views.py` |
| Form | Разбор и проверку входа | `commerce/forms.py` |
| Service | Бизнес-операцию и транзакцию | `commerce/services.py` |
| Model / БД | Данные, связи, ограничения | `commerce/models.py` |
| Template | Отображение уже подготовленных данных | `templates/commerce/` |

Не все приложения требуют абстрактного repository-слоя поверх Django ORM. Добавляйте слой, когда у него появляется конкретная ответственность. Сервис `place_order` полезен: одна операция меняет несколько моделей, имеет инварианты и транзакционные границы. Для простого GET дополнительный сервис может только скрыть читаемый запрос.

Монолит означает общую доставку приложения. Это не означает «весь код в одном файле». `main`, `commerce` и `academy` разделяют предметные области. Микросервисы добавили бы сетевые ошибки, отдельные релизы, наблюдаемость и согласование данных — без доказанной необходимости это усложняет обучение и эксплуатацию.

## Сначала измерения

Предположим, каталог медленный. Проверьте количество SQL-запросов, их план через `QuerySet.explain()`, размер ответа, время рендеринга. В проекте `select_related("category")` убирает отдельный запрос категории для каждого товара. Для обратных связей нужен `prefetch_related`: это отдельный запрос с объединением в Python, а не JOIN в один SQL.

Индекс ускоряет определённый поиск, но занимает место и замедляет запись. Индекс по владельцу и времени заказа соответствует `WHERE owner_id = ... ORDER BY created_at`. Он не решает автоматически медленный поиск по произвольному фрагменту текста. Проверяйте планы на реалистичном объёме данных.

## Кеш — дополнительная копия

Redis и кеширование ответов **не подключены** в проекте. Рассмотрим их как упражнение. Кеш хранит вычисленное значение по ключу с TTL:

```python
# Пример идеи, не текущая реализация каталога.
from django.core.cache import cache

key = "catalog:popular:v1"
result = cache.get(key)
if result is None:
    result = expensive_read()
    cache.set(key, result, timeout=60)
```

Сложнее всего инвалидировать устаревшее значение. Учитывайте фильтры, язык и пользователя в ключе. Нельзя положить страницу личных заказов под общий ключ. Остатки и цены при покупке всё равно перечитываются из БД. Кеш не должен становиться источником истины для списания склада.

## Фоновые задачи

Celery/RQ и broker здесь **не установлены**. Возможный следующий шаг — письмо после заказа. Сетевой вызов внутри транзакции удерживает блокировки во время ожидания почтового сервиса. `transaction.on_commit` переносит действие после фиксации БД, но не гарантирует доставку: процесс может завершиться между commit и отправкой.

Для надёжности применяют transactional outbox: вместе с заказом в той же БД записывается событие «отправить письмо». Отдельный worker выбирает события, отправляет, помечает результат и повторяет после сбоев. Повторы требуют идемпотентности: получатель не должен получить пять писем из-за одного retry. Обычно речь идёт о доставке «как минимум один раз», а не магическом exactly-once.

## Платежи как следующая самостоятельная работа

В магазине нет реальных платежей. Интеграция начинается с sandbox провайдера. Нельзя считать возврат браузера на success-страницу подтверждением оплаты. Нужно проверенное webhook-событие: подпись, сумма, валюта, идентификатор заказа, уникальный event ID. Повтор webhook не должен повторно списывать товар или менять оплаченный заказ в неоплаченный.

Для бронирования склада нужна отдельная модель резерва, срок действия и освобождение. Текущий учебный заказ сразу списывает остаток; не подключайте к нему реальные деньги без проектирования жизненного цикла.

## Async, CPU и I/O

`async` полезен, когда приложение ждёт множество независимых I/O-операций. Он не ускоряет тяжёлые вычисления сам по себе. Блокирующий вызов внутри event loop блокирует другие задачи. Для CPU-задач рассматривают процессы/очередь, для SQL — оптимизацию запросов и ограничения соединений. Сначала правильность и измерения, потом смена модели выполнения.

## Практика

Нарисуйте границы `place_order`. Добавьте в своей ветке интерфейс уведомления и тест, доказывающий отсутствие отправки при откате. Затем спроектируйте outbox таблицу с retry-счётчиком и уникальным ID события; реализацию выполняйте отдельным упражнением.

**Проверка:** можете объяснить поведение при сбое в каждой точке: до commit, после commit, после отправки до отметки «готово».

**Самопроверка:** почему кеш не лечит N+1? Когда монолит удобнее микросервисов? Почему задача должна выдерживать повтор? Какие данные нельзя разделять между пользователями?

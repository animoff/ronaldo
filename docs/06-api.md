# JSON API: контракт между программами

**До начала:** HTTP, авторизация и ORM. **Результат:** вы умеете читать API, проверять его ответы и проектировать ограниченный, предсказуемый интерфейс.

## Представление меняется, правила остаются

HTML предназначен человеку, JSON — другой программе. API не должно обходить права и бизнес-правила ради удобства клиента. В проекте реализовано API чтения: список товаров, отдельный товар и заказы текущего пользователя. Изменения корзины и оформление идут через HTML-формы. Это выбранный объём проекта, а не полный набор REST-операций магазина.

```bash
curl -i 'http://127.0.0.1:8000/api/products/'
curl -i 'http://127.0.0.1:8000/api/products/?page=1'
curl -i 'http://127.0.0.1:8000/api/orders/'
```

Последний запрос без сессии должен получить отказ в аутентификации, а не список чужих заказов. Адрес отдельного товара — `/api/products/<slug>/`; берите реальный slug из списка. Если slug содержит кириллицу, клиент должен корректно кодировать URL.

## Контракт — больше, чем «валидный JSON»

Клиенту нужны стабильные названия полей, типы, смысл значений, правила пагинации и ошибки. Суммы передаются строками для сохранения десятичной точности. Дата должна иметь документированный формат и часовой пояс. Идентификатор нельзя считать доказательством права доступа.

Сериализация означает перевод объекта в передаваемые данные. Не отдавайте `model.__dict__`: туда могут попасть внутренние поля или будущая служебная информация. В API явно выбирается набор полей. Полный актуальный контракт смотрите в `commerce/api.py` и его тестах — именно они определяют реальные ключи ответа.

Пример для обсуждения контракта, а не обещание точного ответа каждой ручки:

```json
{
  "id": 12,
  "name": "Футболка Python",
  "price": "2490.00"
}
```

`2490.00` строкой сохраняет точность и формат. Клиент решает, как отображать валюту; сервер проверяет стоимость заказа самостоятельно.

## Пагинация, ошибки и доступ

Пагинация ограничивает работу БД и размер ответа. Входной номер страницы нужно проверять, а порядок результатов задавать явно: без сортировки одна строка может попасть на разные страницы. При больших данных offset-пагинация становится дорогой; cursor-пагинация — отдельный следующий шаг, здесь она не предполагается.

Используйте подходящий HTTP-статус. Отсутствующий товар — 404, недопустимый параметр — ошибка клиента согласно контракту ручки, неподдерживаемый метод — 405. Не возвращайте всегда `200` с `"error"` внутри: клиентам и мониторингу сложнее отличить успех.

В этом проекте используется сессионная аутентификация Django. JWT не подключён и не нужен только потому, что ответ имеет формат JSON. Если добавить методы записи с cookie-аутентификацией, CSRF-защита остаётся необходимой. CORS определяет, какие браузерные источники могут читать ответ; это не аутентификация и не защита от произвольного серверного клиента.

## Практика

1. Сравните `Content-Type` у каталога HTML и `/api/products/`.
2. Посмотрите ответ списка и сформулируйте контракт каждого поля собственными словами.
3. Запросите отсутствующий slug и проверьте статус и JSON-тело.
4. После входа в браузере откройте `/api/orders/`. Сопоставьте результат с HTML-списком своих заказов.
5. Предложите контракт `POST /api/orders/`: какие данные нужны, какие брать запрещено, где проверить ключ повторной отправки? Реализацию делайте отдельным упражнением с тестами.

**Проверка:** ни публичный список товаров, ни JSON заказа не должны раскрывать пароли, сессионные ключи или чужие данные доставки.

**Типичные ошибки:** раскрывать все поля модели; использовать клиентскую цену; делать выдачу без верхнего ограничения; переносить права в JavaScript; путать CORS с авторизацией.

**Самопроверка:** почему одного JSON-синтаксиса недостаточно для контракта? Можно ли иметь API без DRF? Что сломается у клиента при переименовании поля без согласования?

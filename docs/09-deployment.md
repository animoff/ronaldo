# PostgreSQL, Docker и развёртывание

**Перед уроком:** пройдите тесты и транзакции. Цель — понять, какие процессы нужны приложению, где живут данные и почему запуск на ноутбуке отличается от эксплуатации.

## Что запускается

`runserver` — сервер разработки с перезагрузкой кода. В production WSGI-сервер Gunicorn запускает несколько worker-процессов, каждый принимает запросы и вызывает Django. Перед ним обычно работает reverse proxy: завершает TLS, ограничивает размер запроса, раздаёт часть файлов. PostgreSQL — отдельный процесс. Остановка Django не должна уничтожать данные базы.

`ronaldu/wsgi.py` экспортирует callable `application`; `ronaldu/asgi.py` — ASGI-эквивалент. Наличие ASGI-файла не делает синхронный ORM асинхронным. WebSocket и ASGI-server в этом проекте пока не используются.

## От SQLite к PostgreSQL

SQLite хранит базу в одном файле. Это удобно для первых упражнений. Она не реализует PostgreSQL-блокировки строк; при конкурентной записи может возникать `database is locked`. PostgreSQL нужен для опыта с несколькими покупателями, блокировками и отдельным сервером данных.

Настройки переключаются при непустом `POSTGRES_DB`. Заполните `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_HOST`, `POSTGRES_PORT` в локальном `.env`. Существующие записи SQLite автоматически в PostgreSQL не переносятся. Примените миграции, затем создайте демонстрационные данные:

```bash
python manage.py migrate --noinput
python manage.py seed_demo
python manage.py test --verbosity 2
```

Django создаёт отдельную тестовую базу. Учебной PostgreSQL-роли требуется право `CREATEDB`; production-роли такое право обычно не нужно. Никогда не запускайте тесты с production-учётными данными.

## Docker Compose для локальной практики

Установите Docker с Compose. Скопируйте `.env.example` в `.env` и задайте собственный непустой `POSTGRES_PASSWORD`. Пароль не коммитьте.

```bash
docker compose up --build -d
docker compose exec web python manage.py seed_demo
docker compose exec web python manage.py createsuperuser
docker compose logs --tail 100 web
docker compose exec web python manage.py test
docker compose down
```

`compose.yaml` создаёт PostgreSQL и web. База доступна web-контейнеру по имени `db`; `127.0.0.1` внутри web означает сам web, а не контейнер базы. Порт сайта опубликован только на loopback хоста. Named volume сохраняет БД между перезапусками. `docker compose down -v` **удаляет** volumes и данные — не используйте эту команду, если хотите их сохранить.

Compose-файл здесь — локальная лаборатория с `DEBUG=1`. Для публичного сервера его конфигурацию надо адаптировать. В DEBUG наш URLconf добавляет Django-раздачу media, поэтому учебные фотографии работают и в Compose. В production этот маршрут выключен: для загрузок нужен отдельный media-сервер или объектное хранилище.

## Статика и media — разные данные

`static/css/site.css` — код приложения. `collectstatic` собирает CSS и файлы админки в `staticfiles/`. В production WhiteNoise отдаёт их с хешированными именами: новый CSS получает новый URL и не застревает в браузерном кеше.

`media/` — пользовательские загрузки, их нельзя пересоздать из Git. Для production нужны постоянное хранилище, ограничения файлов, отдельный origin для раздачи и резервные копии. WhiteNoise не предназначен для динамических загрузок.

## Последовательность production deploy

1. Подготовьте PostgreSQL, отдельную роль приложения, резервное копирование.
2. Установите `requirements.txt` в чистое окружение.
3. Задайте случайный длинный `SECRET_KEY`, `DEBUG=0`, точные `ALLOWED_HOSTS` и HTTPS `CSRF_TRUSTED_ORIGINS`. Секреты храните в secret manager/окружении, не в образе.
4. Запустите тесты в отдельной базе.
5. Сделайте backup перед рискованной миграцией; примените `migrate` один раз отдельным deploy-шагом.
6. Выполните `collectstatic --noinput` с production-настройками.
7. Запустите `python manage.py check --deploy --fail-level WARNING`.
8. Запустите `gunicorn ronaldu.wsgi:application --bind 127.0.0.1:8000 --workers 2` и reverse proxy с HTTPS.
9. Проверьте `/health/`, вход, каталог и заказ. Следите за частотой 5xx, временем ответов и числом соединений.

Число worker-процессов подбирают измерениями по CPU/RAM и соединениям БД. Больше не всегда быстрее. `TRUST_X_FORWARDED_PROTO=1` включайте только если доверенный proxy перезаписывает соответствующий заголовок. Иначе клиент сможет подделать сведения о HTTPS.

## Backup и восстановление

`pg_dump` создаёт логическую резервную копию. Передавайте параметры соединения безопасно, например через защищённый `.pgpass`, а не пароль в истории команд. Восстановление проверяйте на **новой пустой** базе через `pg_restore`. Backup считается полезным после проверенного восстановления и проверки данных. Копии должны храниться отдельно от диска сервера; доступ к ним тоже ограничивают.

## Практика и проверка

Запустите локальную PostgreSQL-конфигурацию, создайте заказ, перезапустите web и убедитесь, что заказ остался. Выполните тесты: PostgreSQL-проверки гонок должны исполниться, а не быть пропущены. Остановите базу в учебном окружении и проверьте, что readiness возвращает 503. Верните сервис.

**Типичные ошибки:** хранить БД в слое контейнера; забыть migrations; публиковать DEBUG-страницы; делать migration в каждом worker; считать зелёный health проверкой всех бизнес-функций.

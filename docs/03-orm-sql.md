# Модели, SQL, миграции и ORM

**До начала:** путь HTTP-запроса. **Результат:** вы понимаете устройство данных магазина и умеете отличать удобный ORM-запрос от дорогого или небезопасного.

## Модель — описание, таблица — данные

`main/models.py` описывает каталог. Категория объединяет товары. У товара есть цена и описание; `ProductSize` связывает товар с размером и хранит остаток именно этой разновидности. `ProductImage` хранит дополнительное изображение. В `commerce/models.py` заказ принадлежит пользователю и содержит строки заказа.

```text
Category 1 ── N Product 1 ── N ProductSize N ── 1 Size
                   │
                   └── 1 ── N ProductImage
User     1 ── N Order   1 ── N OrderItem
```

Первичный ключ идентифицирует строку. Внешний ключ ссылается на другую таблицу. `on_delete` описывает поведение удаления связи. Его выбор зависит от смысла: удаление товара не должно стирать финансовую историю завершённого заказа. Поэтому строки заказа хранят снимки названия и цены.

Уникальность `slug` помогает искать товар по человекочитаемому адресу. Одной проверки в Python недостаточно: два процесса могут одновременно пройти её. Уникальное ограничение в БД служит последней защитой. Аналогично, невозможные цены и остатки должны ограничиваться как валидацией, так и схемой, где это применимо.

## От модели к таблице

Миграция — версионируемый переход схемы. Команды имеют разные назначения:

```bash
python manage.py makemigrations --check --dry-run
python manage.py showmigrations
python manage.py migrate
python manage.py sqlmigrate main 0001
```

Первая команда проверяет, не забыта ли миграция; она ничего не сохраняет. `makemigrations` без этих флагов создаёт файл после изменения моделей. `migrate` применяет миграции к выбранной базе. Не редактируйте уже применённую общую миграцию ради нового изменения: создайте следующую и проверьте её на данных.

Не путайте миграции с демо-наполнением. `seed_demo` создаёт примеры для разработки, а не определяет схему и не заменяет резервную копию.

## QuerySet ленивый

```python
products = Product.objects.filter(is_active=True).select_related("category")
# Здесь мы построили описание запроса.
for product in products[:5]:
    print(product.name, product.category.name)
# Здесь запрос понадобился и был выполнен.
```

`filter()` возвращает QuerySet, `get()` — один объект или исключение, `first()` — объект либо `None`. `exists()` отвечает на вопрос о наличии, `count()` считает строки. Используйте метод под нужный результат, а не загружайте тысячи объектов, чтобы узнать их число.

ORM переводит операции в SQL и параметризует значения. Не собирайте SQL конкатенацией пользовательского текста. ORM не отменяет знания SQL: нужно понимать `SELECT`, `JOIN`, `WHERE`, `ORDER BY`, `GROUP BY` и планы выполнения.

## N+1 и индексы

Если после загрузки N товаров отдельно получать категорию каждого, получится один основной запрос плюс N дополнительных. `select_related()` присоединяет одиночные связи через JOIN; `prefetch_related()` загружает множественные связи отдельным запросом и соединяет их в Python. Они не взаимозаменяемы.

Индекс ускоряет подходящие поиски и сортировки, но занимает место и увеличивает стоимость записи. Индекс не стоит добавлять на каждое поле. Сначала измерьте запрос: в PostgreSQL используйте `EXPLAIN`, затем при необходимости `EXPLAIN ANALYZE` на безопасном запросе и подходящих данных.

## Практика

1. В shell найдите три активных товара и выведите названия категорий через `select_related`.
2. Посмотрите `str(queryset.query)`. Определите условие фильтрации и JOIN.
3. Создайте категорию с уже существующим slug в экспериментальной БД. Ожидайте отказ ограничения, а не вторую одинаковую запись.
4. Найдите `related_name` у `ProductSize`. В первоначальном коде сохранено имя `prduct_size`; используйте актуальный интерфейс модели, не угадывайте его по английскому слову.
5. Объясните, как получить товары дороже заданной суммы: используйте `Decimal`, `price__gt`, явный порядок.

**Проверка:** прочитайте SQL начальной миграции и найдите внешние ключи. Изменение моделей без миграции должно обнаруживаться проверочной командой.

**Типичные ошибки:** `get()` для нескольких строк; запрос на каждой итерации; удаление миграций ради «исправления» общей БД; ожидание одинаковых конкурентных гарантий SQLite и PostgreSQL.

**Самопроверка:** почему проверка уникальности формы не заменяет ограничение БД? Когда `prefetch_related` полезнее JOIN? Почему цена заказа не должна вычисляться из текущей цены товара?

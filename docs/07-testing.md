# Тестирование: доказываем поведение

**До начала:** основной путь от каталога до заказа. **Результат:** вы умеете написать проверку, которая обнаружит настоящий дефект и объяснит его причину.

## Тест проверяет обещание

«Страница открылась» не доказывает, что списание безопасно или чужие заказы закрыты. Хороший тест формулирует наблюдаемое поведение: покупатель получает свой заказ, остаток уменьшается один раз, ошибка второй позиции откатывает первую.

В проекте используется стандартный тестовый runner Django, а не pytest:

```bash
python manage.py test
python manage.py test main
python manage.py test commerce --verbosity 2
python manage.py check
python manage.py makemigrations --check --dry-run
```

Последние две команды полезны, но не заменяют тесты поведения. Успешный запуск с «0 tests» не подтверждает работоспособность. Читайте количество и итог: passed, skipped и expected failure означают разное.

## Arrange, Act, Assert

1. **Arrange:** подготовить пользователя, товар, остаток.
2. **Act:** выполнить операцию через нужный интерфейс.
3. **Assert:** проверить ответ и важные изменения состояния.

```python
from decimal import Decimal
from django.test import TestCase
from main.models import Category, Product


class PriceExample(TestCase):
    def test_decimal_price_is_preserved(self):
        category = Category.objects.create(name="Учёба", slug="study")
        product = Product.objects.create(
            name="Пример", slug="example", category=category,
            color="синий", price=Decimal("19.90"),
        )
        product.refresh_from_db()
        self.assertEqual(product.price, Decimal("19.90"))
```

Это небольшой пример структуры, а не достаточный тест магазина. `refresh_from_db()` перечитывает объект: после `QuerySet.update()` старый Python-экземпляр сам не обновляется. Тест, сравнивающий только уже присвоенную переменную, может вообще не проверить запись в БД.

## TestCase, клиент и база

`django.test.TestCase` изолирует изменения тестов с помощью транзакций. Django создаёт отдельную тестовую БД; не направляйте тесты на production и не отключайте защиту ради удобства. `TransactionTestCase` нужен, когда проверяется реальное поведение транзакций, коммитов и соединений. Он обычно медленнее.

Тестовый `Client` отправляет запросы внутри Django без запуска сетевого сервера. `force_login()` полезен для проверки авторизации: он не тестирует пароль. Для самого входа используйте реальный POST формы и проверяйте результат.

По умолчанию тестовый клиент не требует CSRF-токен. Для проверки CSRF создайте `Client(enforce_csrf_checks=True)`. Иначе тест «POST без токена разрешён» ничего не говорит о production-поведении.

## Какие проверки наиболее полезны

- модели: ограничения цены, уникальность размера товара, генерация slug;
- каталог: фильтрация, пагинация, скрытый неактивный товар;
- корзина: ноль удаляет, отрицательное или недопустимое количество не принимается;
- заказ: цена сохраняется снимком, остаток списывается, отказ откатывает изменения;
- доступ: анонимный запрос закрыт, один пользователь не видит заказ другого;
- API: контракт полей, тип суммы, пагинация и ошибочные параметры;
- повтор: одинаковый ключ не создаёт второй заказ.

Моки нужны для внешней границы — например, недоступного почтового сервиса. Не замокайте весь ORM в интеграционном тесте оформления: тогда легко «доказать» то, что база на самом деле не умеет. SQLite подходит для быстрого старта, PostgreSQL нужен для проверки используемых гарантий именно этой БД.

## Практика

1. Запустите отдельный существующий тест с `--verbosity 2` и найдите его подготовку, действие и проверки.
2. В своей ветке намеренно уберите фильтр владельца заказа. Соответствующий тест должен упасть. Верните изменение.
3. Добавьте тест граничного количества: ровно весь остаток и на единицу больше.
4. Напишите регрессионный тест до исправления выбранного дефекта: сначала красный запуск, затем исправление и зелёный.

**Проверка:** тест должен падать при нарушении правила. Если он проходит после удаления проверяемой логики, он слабый.

**Типичные ошибки:** тестировать внутренние имена вместо поведения; полагаться на порядок тестов; забывать перечитать БД; считать замоканный внешний ответ подтверждением реальной интеграции.

**Самопроверка:** что проверяет `force_login`, а что пропускает? Когда нужен сетевой smoke test поверх тестового клиента? Почему 100% покрытия строк не означает отсутствие ошибок?
